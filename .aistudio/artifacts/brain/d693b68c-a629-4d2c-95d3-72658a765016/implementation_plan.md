# إصلاح اكتشاف أصول إصدار GitHub ومعالجة خطأ 404 (MTX Native Downloader)

خطة دقيقة ومحكمة لإصلاح نظام تنزيل محرك MTX الأصلي واكتشاف أصول إصدار GitHub الرسمي، معالجة الخطأ 404، وضمان استرجاع الروابط الصحيحة بدقة واختيار المعمارية المتوافقة.

---

## مراجعة وتأكيد القرارات الرئيسية (Confirmed Decisions)

> [!IMPORTANT]
> **التشخيص والقرارات المؤكدة:**
> - **السبب الجذري لخطأ 404:**
>   1. كان الكود يعتمد على استدعاء `/releases/latest` بدلاً من وسم الإصدار الفعلي الخاص بالمحرك (`0.0.1`).
>   2. عند فشل العثور على أصل مطابق، كان الكود يقوم بتركيب الرابط يدوياً بنمط غير صحيح (`https://github.com/.../releases/download/v2.1.9/...`) وهو مسار غير موجود على خوادم GitHub وينتهي فوراً برمز 404.
>   3. ملفات الأصول في الإصدار `0.0.1` مرفقة بروابط تنزيل مباشرة (`user-attachments`) بينما كان الكود يبحث فقط في حقل `assets` التقليدي، وحين يجدها فارغة يفشل وينتقل للرابط الوهمي.
> - **المستودع المعتمد:** تم التحقق منه مباشرة من الإعدادات والروابط: مستودع التطبيق الرسمي هو `Nexusap` التابع للمالك `zxiu86`.
> - **وسم الإصدار المستهدف:** الاستعلام المباشر عن الإصدار بالوسم `0.0.1` (`repos/zxiu86/Nexusap/releases/tags/0.0.1`) مع دعم البحث في قائمة الإصدارات كخيار احتياطي.
> - **مطابقة الأصول:**
>   - معمارية `arm64-v8a` ← `libmtx_v8a.zip`
>   - معمارية `armeabi-v7a` ← `libmtx_v7a.zip`
> - **استخراج روابط التنزيل:** الحصول على الرابط المباشر دون أي تركيب يدوي عبر `browser_download_url` أو روابط المرفقات المباشرة في متن الإصدار.

## 1. النظرة العامة والهدف التقني (Overview & Technical Goal)

ضمان استقرار وموثوقية تنزيل محرك **Olympus MTX** الأصلي عبر:
1. استعلام دقيق لواجهة برمجة تطبيقات GitHub (GitHub REST API v3) لاستهداف الوسم `0.0.1` مباشرة.
2. فحص الأصول المتاحة في مصفوفة `assets` واستخراج الروابط الموثوقة من `browser_download_url`.
3. دعم روابط مرفقات التنزيل في متن الإصدار (`release.body`) كحماية إضافية في حال تم رفع الملفات كمرفقات ماركداون.
4. اكتشاف المعمارية المناسبة لجهاز المستخدم (`Build.SUPPORTED_ABIS`) ومنع اختيار مكتبة غير متوافقة.
5. استخراج الحجم الفعلي للبايتات ديناميكياً من حقل `size` أو عبر استعلام `Content-Length`.
6. معالجة عمليات إعادة التوجيه (HTTP 302/301 Redirects) الخاصة بـ GitHub CDN بأمان.
7. تسجيل تشخيصي شامل ودقيق (Diagnostic Logging) بدون تسجيل رموز الوصول أو البيانات الحساسة.
8. الحفاظ التام على خطوات التحقق من سلامة الأرشيف، فك الضغط، تهيئة JNI، وتصميم واجهة المستخدم الحالية.

## 3. خطة التعديلات خطوة بخطوة (Detailed Implementation Steps)

### الخطوة 1: تحديث واجهة GitHub API (`GitHubApiService.kt`)
- إضافة نقطة نهاية مخصصة للاستعلام عن الإصدار بواسطة الوسم:
  ```kotlin
  @GET("repos/{owner}/{repo}/releases/tags/{tag}")
  @Headers("Accept: application/vnd.github.v3+json, application/json")
  suspend fun getReleaseByTag(
      @Path("owner") owner: String,
      @Path("repo") repo: String,
      @Path("tag") tag: String
  ): Response<GitHubReleaseDto>
  ```

### الخطوة 2: تحسين اكتشاف المعمارية والمكتبة المتوافقة (`ResourceSetupManager.kt`)
- فحص دقيق لمصفوفة `Build.SUPPORTED_ABIS`:
  - إذا كان يدعم `"arm64-v8a"`: اختيار الهدف `"arm64-v8a"` واسم الملف المتوقع `"libmtx_v8a.zip"`.
  - إذا كان يدعم `"armeabi-v7a"` أو `"armeabi"`: اختيار الهدف `"armeabi-v7a"` واسم الملف المتوقع `"libmtx_v7a.zip"`.
  - التحقق من دعم المعمارية وإلقاء خطأ توضيحي في حال كانت المعمارية غير مدعومة نهائياً.

### الخطوة 3: تصحيح اكتشاف الإصدار واستخراج الروابط (`ResourceSetupManager.kt`)
- استهداف الإصدار `0.0.1` مباشرة في مستودع `Nexusap`.
- فحص استجابة الـ API وإضافة سجلات تشخيصية واضحة (`Log.d` / `Log.i` / `Log.w`):
  - تسجيل كود استجابة الـ API (`API response status`).
  - تسجيل الوسم الذي تم حله (`Resolved release tag: 0.0.1`).
  - تسجيل أسماء الأصول المتاحة (`Available assets in release`).
  - تسجيل المعمارية المختارة والأصل المستهدف (`Selected ABI` و `Selected asset name`).
- مطابقة الأصول بالاسم الصريح (`libmtx_v8a.zip` أو `libmtx_v7a.zip`).
- في حال كانت مصفوفة `assets` فارغة في الـ JSON واستخدم الإصدار مرفقات الماركداون، يتم استخراج الرابط المباشر من متن الإصدار (`release.body`) عبر التعابير النمطية بدقة تامة.
- **منع منعاً باتاً** تركيب روابط وهمية تؤدي إلى 404.

### الخطوة 4: تنزيل الملف ومتابعة التحويلات ومعالجة الأخطاء
- استخدام `OkHttpClient` مع دعم متابعة الـ Redirects (`followRedirects = true`).
- قراءة الحجم الحقيقي بدقة من `asset.size` أو جلب `Content-Length` الفعلي عبر طلب `HEAD`.
- معالجة الأخطاء المحددة:
  - كود 404: توضيح ما إذا كان المستودع، الإصدار أو ملف الأصل غير موجود.
  - كود 401 / 403: توضيح خطأ الصلاحيات أو تجاوز حد استعلامات GitHub API.
  - فقدان الأصل: عرض اسم الأصل المطلوب بدقة مع إمكانية إعادة المحاولة.
  - انقطاع الاتصال: إمكانية إعادة المحاولة عند توفر الإنترنت.

### الخطوة 5: التحقق والاختبار الشامل
- بناء المشروع والتأكد من نجاح `compile_applet`.
- كتابة وتشغيل اختبار وحدة (`UnitTest`) للتحقق من:
  1. دقة استعلام الـ API واكتشاف الإصدار `0.0.1`.
  2. مطابقة أسماء الملفات `libmtx_v8a.zip` و `libmtx_v7a.zip`.
  3. استرجاع الروابط المباشرة الصحيحة وحجمها الفعلي.
  4. محاكاة حالات الخطأ والتعامل معها بنجاح.
